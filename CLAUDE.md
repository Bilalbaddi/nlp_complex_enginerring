## Decisions (defaults chosen; change here if revisited)
- **Sync SQLAlchemy 2.x + psycopg 3** (FastAPI runs sync endpoints in a threadpool). Simpler with geoalchemy2/pgvector; fine for this scale.
- **DECISION (user, after Phase 1): Supabase is the ONLY external service.** Redis/Upstash and Celery were removed entirely. Postgres does data + cache + job queue + rate limiting; Supabase Storage holds files. No Redis/Celery packages, settings or docs remain. Native run on Windows (no Docker; `docker-compose.yml` is an optional local alternative).
- **Connections:** `DATABASE_URL` = transaction pooler (6543) for the app; `MIGRATION_DATABASE_URL` = SESSION pooler (same host, port 5432) for Alembic and tests. The direct host `db.<ref>.supabase.co` is IPv6-only and unreachable here. `sslmode=require` is added to any non-local host (`normalize_db_url`); psycopg uses `prepare_threshold=None` for pooler compatibility. Special chars in the password must be URL-encoded (`@` -> `%40`).
- **Latency:** the DB is remote (~340 ms per round trip from the dev machine). `pool_pre_ping` adds one round trip per checkout (kept for reliability). Keep endpoints to few queries, batch writes, and cache analytics in `cache_entries`. The full test suite takes several minutes for the same reason.
- **Row-level security:** Supabase exposes `public` tables via its REST API to holders of the public anon key. Every app table has RLS ENABLED with NO policies (only the backend's direct DB role can access). **Every new migration that creates a table MUST also `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`** (`tests/test_storage.py::test_every_table_has_row_level_security` fails otherwise).
- **Storage:** private buckets only, created automatically at API start (`storage.ensure_buckets`, skipped in tests); serve files via short-lived signed URLs or stream through the API. `SUPABASE_SERVICE_ROLE_KEY` is backend-only, never sent to the frontend. Auth stays custom JWT (not Supabase Auth). `SUPABASE_SECRET_KEY` (new-style key) may be in `.env` but the code uses the service-role key.
- **Jobs:** `JOBS_INLINE` unset = true only when `ENV=development`. Tests set it false and call `jobs.run_job()` explicitly. Retries: `JOB_MAX_ATTEMPTS` (3), backoff `JOB_RETRY_BASE_SECONDS * 2^(attempt-1)`, stale `running` jobs are requeued after `JOB_STALE_AFTER_SECONDS`. The worker enqueues `system.cleanup` (expired cache rows, old rate-limit windows, old finished jobs) every 10 min.
- **Extensions** (`postgis`, `vector`) are enabled by migration 0001 (`CREATE EXTENSION IF NOT EXISTS`), never by hand.
- **Tests use a separate schema `sgdss_test`** in the same DB (Supabase can't create databases). conftest sets `DB_SEARCH_PATH=sgdss_test,public,extensions` (applied with `SET search_path` on every connection in `db/session.py` and in Alembic's env.py, including `version_table_schema`), so it REQUIRES the session pooler URL (the transaction pooler and startup `options` do not work). The schema is dropped/recreated per session. Because `public` stays on the path (extension types live there), conftest asserts `to_regclass('users')` etc. resolve to `sgdss_test.*` before any TRUNCATE. (An early version only checked `current_schema()`, which let tests hit `public` tables; fixed.)
- **Storage budget (Supabase 500 MB):** embeddings are pgvector `halfvec` (768 B per 384-d vector). Only `document_chunks` has an HNSW index; complaint embeddings have NO ANN index (near-duplicate search prefilters by ward/category/time window, then exact cosine). `SEED_COMPLAINT_COUNT` defaults to 50,000 (measured: 65.5 MB total incl. feedback/performance/indexes = 13%; +~40 MB when embeddings are stored). Measure with `tasks.py db-size`; it warns above 70%.
- **Model/disk policy (Phase 3+):** CPU-only PyTorch (`--extra-index-url https://download.pytorch.org/whl/cpu`, put in a `requirements-ml.txt`), all model downloads in `MODEL_CACHE_DIR` (default `.cache/models`, git-ignored; task runner exports `HF_HOME`, `SENTENCE_TRANSFORMERS_HOME`, `TORCH_HOME`). Default model `paraphrase-multilingual-MiniLM-L12-v2` (384-d, ~470 MB on disk because of its multilingual vocab). Fallback if disk is tight: an ONNX runtime path (fastembed) without torch. Decide in Phase 3.
- **Embedding dimension 384** (`EMBEDDING_DIM`). Changing it needs a migration.
- Enums stored as strings (`native_enum=False`) to avoid PG enum migration pain.
- Passwords: bcrypt used directly (no passlib), truncated to 72 bytes; schema enforces max 72 bytes and letters+digits, min 8.
- Token model: stateless access (30 min) + refresh (7 days) JWTs, type-checked; no server-side revocation (logout is audited only). Frontend keeps tokens in localStorage (academic scope; note as limitation in docs).
- Error envelope: `{success, data, error: {code, message, details}}`; lists return `data: {items, meta:{page,page_size,total,pages}}`.
- Roles: commissioner, department_head, ward_officer, analyst, admin. Users may carry `department_id` / `ward_id` for data scoping (scoping helpers come with the analytics endpoints).
- `JWT_SECRET` has no usable default; the placeholder is rejected when `ENV=production`. `.env` is git-ignored; `.env.example` is committed.
- Demo emails use the `sgdss.org` domain (email-validator rejects `.local`/special-use domains).
- Requirements are appended per phase (ML libs arrive in Phase 3). Local Python is 3.12; project targets 3.11+.
- **Latency rules (remote DB, ~256 ms per round trip; measured):** transactional session = 3 round trips per read (BEGIN, SELECT, ROLLBACK), autocommit = 1; a new connection takes ~5 s. So: read-only endpoints use `Depends(get_read_db)` (autocommit), single-statement writes (cache, rate limiter) use `AutocommitSession`, only multi-statement writes use `get_db`. The pool is warmed at API start (`warm_pool`), connections are pinged only after 20 s idle (no pre-ping), the authenticated user is cached in-process for `USER_CACHE_SECONDS` (10; tests use 0; `invalidate_user_cache` on user changes), list totals use a window `count(*) over()` in the same query. Bulk inserts MUST be one multi-row `insert(Table).values([...])` (ORM `insert(Model)` + list = one round trip per row: 16x slower). Typical results: cached endpoints ~6 ms, most GETs ~0.3 s.
- `uvicorn --reload` on this OneDrive folder does not reliably pick up edits: if behaviour looks stale, restart `dev-backend` (check the listener's start time).
- Login rate limit: 10/min per IP (`LOGIN_RATE_LIMIT_PER_MINUTE`), counted in the `rate_limits` table. LLM per-user limit setting exists (`LLM_RATE_LIMIT_PER_MINUTE`), used from Phase 7.
- shadcn/ui: not initialised yet; only its foundations (`cn`, cva, tailwind-merge, CSS variables theme with dark mode) are in place. Components are added in Phase 8.

## Conventions
- Type hints everywhere in Python; strict TS, no `any` (ESLint rule enforced).
- Every route returns the envelope (use `ok()` / `make_page()` in `schemas/common.py`; raise `ApiError` for errors). Declare `response_model=Envelope[...]`.
- Every non-health endpoint must depend on `get_current_user` or `require_roles(...)`.
- Sensitive actions call `audit.record(...)`. Never put secrets/passwords in audit `detail`.
- LLM prompts live in `backend/app/llm/prompts/` (files, not inline). Strip PII before any Groq call. Never let the LLM write SQL.
- Tests never call the Groq API (mock the client). They DO use the real Supabase DB (schema `sgdss_test`) and Storage (throwaway objects, deleted after).
- LLM outputs and heavy analytics go through `services/cache.py` (`make_key`, `get_or_set`); long work goes through `services/jobs.py`.
- Bash heredocs with long content failed in this environment's shell; use the Write tool for file creation.
